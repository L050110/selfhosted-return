# 2026-11-13：双向实测（含 B 方向拐点与端口绑定）

> **这篇怎么用**：下面是一份**真实部署的实测示例**，数据已脱敏。
> 重点看三样东西：**测什么、怎么测、量级大概多少**。
> 不要照抄数字——你的链路、时段、对端带宽都不一样，照抄只会得出错误结论。
> 自己怎么测、怎么判断结果对不对，见 [how-to-verify.md](../docs/how-to-verify.md)。


> **方向**：本文两节分属两个方向，已分别标注。
> 第一节是 **B（出国，境内→境外）**，第二节是同一时段的对照与端口验证。
> **与 `2026-11-12-scenario.md` 不是同一次部署**，两文的数字不可混用。

环境：两端 Windows；Tailscale 直连（不落 DERP）；hysteria2 v2.13.0；测速目标 `speed.cloudflare.com`。

---

## 一、链路质量（B 方向：境内 → 境外住宅）

```
30 包 ICMP 到对端 Tailscale IP：
  recv=30/30   min=207 ms   avg=225 ms   max=251 ms
```

**0 丢包、抖动 ±22 ms。**

对照：同一天早些时候（校园网短暂中断刚恢复）测到 `recv=27/30`，jitter 更小但丢了 10%。
**同一条链路，一天之内质量会变**，所以任何吞吐结论都必须带时间戳。

---

## 二、吞吐：Brutal 相对裸 TCP 的倍数

同一对机器、同一路径、同一时段：

| 传输方式 | 吞吐 |
| --- | --- |
| **裸 TCP**（SSH 直拉 13 MB，不套 hysteria） | **0.17–0.36 Mbps** |
| **hysteria2 + Brutal**（20 MB 单流） | **7.0–7.5 Mbps** |

**20–44 倍。**

TCP 侧的数学：`MSS/(RTT×√p) = 1460/(0.225×√0.1) ≈ 0.16 Mbps`，与实测同量级。
**这不是配置问题，是 TCP 在这条路上活不了。**

> 裸 TCP 用 SSH 测是因为它天然走 TCP 且不需要额外装东西。
> 数字偏低还有 SSH 自身加密和窗口因素，但量级足以说明问题。

## 三、`bandwidth.down` 拐点（B 方向）

同方向、同路径、只改声明值：

| 声明 | 20 MB 用时 | 扣除 TTFB 后有效吞吐 | 占声明 |
| --- | --- | --- | --- |
| 8 mbps | 21.69 s | **7.70 Mbps** | ≈100% |
| 10 mbps | 21.29 s | 7.77 Mbps | 81% |
| 12 mbps | 22.47 s | 7.35 Mbps | 64% |

**结论：声明 8 时已满额，再高只是超发。**

> 计算方式：`字节数×8 / (time_total − ttfb)`。
> 直接用 `curl -w %{speed_download}` 会把 TTFB 算进分母，凭空少 4–5%。

## 四、路径 MTU

```
ping -f -l 1275 → 3/3 通   （总包 1303）
ping -f -l 1300 → 0/3 不通 （总包 1328）
```

与 Tailscale 接口 MTU **1320** 一致：超过 1320 需要隧道内分片，分片被丢弃。
hysteria2 默认 1200，装得下，**不分片**。

> 用 `Test-Connection -DontFragment` 会得到「全部 FAIL」——
> PowerShell 5.1 没有这个参数，参数不存在时不报错、只返回空。假阴性，坑过一次。

## 五、对端（境外那台）自身能力

绕开隧道、直连本地 CDN：

| 指标 | 值 |
| --- | --- |
| 上行 | **22.0 Mbps**（13.1 MB / 4.77 s） |
| 下行 | **342 Mbps** |
| 接入方式 | WLAN（Wi-Fi），链路速率 866.7 Mbps，RSSI −54 dBm，5 GHz |

**注意**：22 Mbps 是到本地 CDN 的**短途**数字，不代表洲际段可用带宽。
B 方向隧道内只有 7–7.5 Mbps，两者不可互相换算——中间隔着洲际段。

Wi-Fi 侧信号很好（−54 dBm / 86%），**不是瓶颈**。
换有线能改善的是**抖动和隐藏重传**，不是峰值。

## 六、端口绑定出口：一次绑定，三处统一

`listeners` 里把 7896 绑死到出口节点，浏览器用
`--proxy-server="socks5://127.0.0.1:7896"`。

| 指标 | 走规则表 | 绑 7896 |
| --- | --- | --- |
| 中国出口 IPv4 | 本地 IP（本地ISP） | **住宅 IP（对端）** |
| Cloudflare 出口 | <第三方出口IP>（第三国） | **住宅 IP（对端）** |
| 使用的出口 IP | 住宅 IP | 住宅 IP |
| DNS 出口 | <本地ISP的DNS>（本地 ISP） | **对端 ISP 的 DNS** |
| WebRTC UDP | 第三国 | **仍为第三国（未解决）** |

**DNS 跟着出口走了**——这是意外收获。之前判定「DNS 泄露」是隐私问题、不是风控信号，
但在绑端口之后它自动消失了，说明它原本的成因就是「DNS 没跟出口走」。

### WebRTC 为什么没解决

浏览器参数 `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` **已生效**
（进程命令行里确认带上了），但 WebRTC 仍泄漏。

**根因**：本地代理内核工作在 **TUN 模式**，在**操作系统路由层**就把 UDP 接走了。
浏览器参数管的是「浏览器自己的代理逻辑」，管不到 OS 路由。

另外 Chromium 的 WebRTC **不支持通过 SOCKS5 转发 UDP**（只代理 TCP），
所以即使指定了 `--proxy-server=socks5://`，STUN 的 UDP 仍会落到系统路由上。

**判定：不修。** 三条路（改注册表策略 / 关 TUN / 按 DST-PORT 改规则）代价都大于收益，
而且多数站点并不拿 WebRTC 当风控信号。详见 pitfalls 坑 10。
