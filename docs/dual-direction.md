# 双向：两个方向、两条链路、两个上限

> 这套方案不是「一个隧道」，是**两台机器互为出口**。
> 把方向搞混，是这份文档诞生以来最容易犯的错，所以单独开一篇。

---

## 一句话区别

| | **A 方向：回国** | **B 方向：出国** |
| --- | --- | --- |
| 使用者人在 | **境外** | **境内** |
| 出口在 | **境内**（境内那台的住宅 IP） | **境外**（境外那台的住宅 IP） |
| 服务端装在哪 | 境内那台 | 境外那台 |
| 客户端装在哪 | 境外这台 | 境内这台 |
| 解决什么问题 | 人在国外，打不开政务/银行/票务，视频卡 | 人在国内，需要海外住宅 IP（注册、验证、分区内容、价格查询） |
| 出口 IP 类型 | 境内住宅 | 海外住宅 |

**两台机器同时是 A 的服务端和 B 的客户端**（或者反过来），这就是「双向」的意思。
不需要四台机器，两台就够。

```
        A 方向（回国）                    B 方向（出国）
   境外这台  ──────▶ 境内那台       境外这台  ◀────── 境内这台
   (client)           (server)       (server)          (client)
       │                 │               │                │
       └─── 访问境内站点 ─┘               └── 访问境外站点 ──┘
```

---

## 两条链路的上限是**各自算**的

这是最容易搞错的地方：**两个方向的吞吐上限不一样，而且可能差一个数量级。**

```
任一方向的上限 = min(发送端上行, 路径有效吞吐)
```

| | A 方向（回国） | B 方向（出国） |
| --- | --- | --- |
| 发送端 | 境外那台（出海宽上行） | 境外那台（出海宽上行） |
| 实测上行 | ~99 Mbps（校园网/商宽） | 22 Mbps（住宅 cable 上行） |
| 路径交出 | **99.4 Mbps** 单流 | **7.0–7.5 Mbps** |
| 相差 | — | **13 倍** |

**同一个 `hysteria2` 二进制、同一对机器、同一段代码，两个方向差了 13 倍。**
原因不在软件，在两个方向走的国际段质量不同（拥塞程度、丢包率、出口带宽套餐）。

> **所以：不要拿 A 方向的 99 Mbps 去承诺 B 方向。** 它们不是同一条链路。
> 仓库里 `measurements/` 下每份实测都标注了方向，看之前先确认这一行。

## 拓扑（以 A 方向为例，B 方向把两端对调即可）

```
使用者机器 (境外)
  │  Clash / mihomo  (mixed-port，负责分流)
  │      └─ 只把需要的域名/IP 送进下面这条
  ▼
hysteria2 client  ──QUIC(Brutal)──▶  Tailscale tunnel (WireGuard)
                                        │
                                        ▼
                              出口机器 (境内，住宅宽带)
                                        │
                                        ▼
                                  目标站点
```

**注意：hysteria2 是套在 Tailscale 里跑的。** 具体做法是客户端连对端的
**Tailscale IPv4（100.x.x.x）**，不是公网 IP。这带来两个后果：

1. 好处：不需要公网 IP、不需要端口映射、两端 NAT 后也能通，直连打洞失败会自动落 DERP
2. 代价：多一层封装，约 5–8% 带宽开销；MTU 受 Tailscale 限制（见下）

---

## MTU：这条链路的硬边界

首包到底多大，取决于 **Chrome-parrot 是否开启**：

| 模式 | 线上首包（UDP 载荷） | +28 后总包 | 需要网卡 MTU |
| --- | --- | --- | --- |
| **parrot 开**（hysteria 默认，`disableChromeParrot: false`） | **1250** | 1278 | ≥ 1280 |
| parrot 关（`disableChromeParrot: true`） | **1280** | 1308 | ≥ 1308 |
| quic-go 下限 `MinInitialPacketSize` | 1200 | 1228 | ≥ 1228 |
| **Tailscale 默认网卡** | — | — | 1280（只够第一行） |
| **本项目建议** | — | — | **1320** |

出处：apernet/quic-go fork `internal/protocol/params.go` 的
`const InitialPacketSize = 1280`，以及 `chrome_parrot.go` 的
`chromeInitialPacketSize = 1250`（`populateConfig()` 里 parrot 开启时用它覆盖）。

**判据：网卡 MTU < 1308 时，只要有人把 `disableChromeParrot` 打开，握手就会静默挂。**
所以别赌默认值，直接设 **1320**。

> **这里有个容易搞混的点**：很多资料里出现的 `1200` 是 quic-go 的
> `MinInitialPacketSize`（**下限**，配得更小会被抬回 1200），
> 而实际默认发出去的 `InitialPacketSize` 是 **1280**。
> 判断"会不会分片"要用 1280+28=1308，不能用 1200。
>
> 另外 hysteria2 的配置里**没有** MTU 字段——这个值由 quic-go 的默认值决定，
> 想改只能改 `quic.InitialPacketSize`（hysteria 未暴露）或加底层封装。

`1328` 不通不是"MTU 黑洞"，是超过 Tailscale 的 1320 后需要隧道内分片，分片被丢弃。
这是预期行为，不是故障。

**判断方法（PowerShell，两端都可用）：**

```powershell
# 逐级加大，找到「通」的最大值
ping -n 3 -f -l 1275 100.x.x.x   # 通 → 总包 1303
ping -n 3 -f -l 1300 100.x.x.x   # 不通 → 总包 1328
```

> **`ping -f` 是禁止分片。** 用 `Test-Connection` 做这个测试会得到全部 FAIL——
> PowerShell 5.1 的 `Test-Connection` **没有 `-DontFragment` 参数**，参数不存在时
> 它不会报错，只会返回空，看起来像「全部不通」。这个假阴性坑过一次。

## 为什么两个方向都要 hysteria2 + Brutal

B 方向（出国）那一段洲际链路的实测：

| 传输方式 | 吞吐 |
| --- | --- |
| **裸 TCP**（同一对机器、同一路径） | **0.17–0.36 Mbps** |
| **hysteria2 + Brutal** | **7.0–7.5 Mbps** |

**20–44 倍。**

原因不是 hysteria 有什么魔法，是 TCP 在这条路上**从数学上就活不了**：

```
Mathis 估算：throughput ≈ MSS / (RTT × √丢包率)
             ≈ 1460 B / (0.225 s × √0.1)
             ≈ 20 KB/s ≈ 0.16 Mbps
```

225 ms RTT × 10% 丢包，TCP 就只剩这么多。实测 0.36 Mbps，同一量级。

**Brutal 的做法是「无视丢包，按声明速率硬发」**，所以能吃到 7 Mbps。
代价是它必须知道链路真实容量——声明高了会把包灌进瓶颈然后全丢。

## `bandwidth.down` 是硬上限，不是建议值

同一方向、同一路径、只改 `down` 声明：

| 声明值 | 实测吞吐 | 占声明值 |
| --- | --- | --- |
| 8 mbps | 7.38 Mbps | 92% |
| **10 mbps** | **7.52 / 7.30 Mbps** | 75% |
| 12 mbps | 7.12 Mbps | 59% |

**声明越高，实际越低。** 超发的包丢在瓶颈里，重传开销反而挤占有效流量。

所以正确做法是：

1. **声明值 = 这条路径真实能交出的量**，不是「线路带宽」
2. 单流测出拐点，声明在拐点上
3. 别指望声明 20 就能跑到 20

> 上面那句「8 mbps 时 92%」，92% 不是损失：Brutal 按线上的字节算（含 QUIC 头和加密开销约 4%），
> 而实测用 `curl -w %{speed_download}` 时**首字节等待（TTFB）也被算进总时长**（约 4.5%）。
> 两项相乘正好 ~92%，意思是**声明 8 时其实是足额送达的**。

## 两个方向各能干什么

详见 [scenarios.md](scenarios.md)。这里只放结论：

| 能做 | A 方向 | B 方向 |
| --- | --- | --- |
| 政务 / 银行 / 票务（机房 IP 常被拒） | ✅ 这是它的主场 | — |
| 视频站（1080p） | ✅ | ✅ |
| 分区流媒体 | — | ✅ 1080p 以内 |
| 需要住宅 IP 的注册 / 验证 | — | ✅ 唯一不可替代的价值 |
| 远端执行命令（SSH） | ✅ | ✅ |
| 4K / 在线游戏 / 大文件备份 | ❌ | ❌ |
| 多人共用 | ❌ | ❌ |
