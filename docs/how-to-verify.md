# 怎么判断：数据是不是真的、配置对不对、做没做成

> 这篇不讲怎么装，讲**怎么知道自己装对了**。
> 这类项目最容易犯的错不是配置写错，是**测错了却以为测对了**。

---

## 一、先说测量方法本身的坑

**测量方法错了，后面所有结论都是错的。** 下面五条按踩到的频率排。

### 坑 A：`speed_download` 把首字节等待算进去了

```powershell
curl.exe -w "time=%{time_total} speed=%{speed_download}"
```

`%{speed_download}` = `字节数 / time_total`，而 `time_total` **包含 DNS、建连、等首字节（TTFB）**。

一条 300 ms RTT 的链路上，TTFB 通常 0.7–1.1 秒。摊进 20 秒的传输里，凭空少 4–5%。

**正确算法：**

```
有效吞吐 = 字节数 × 8 / (time_total − ttfb)
```

**控制变量法更简单：把文件加大。** 20 MB 时 TTFB 占 4%，200 MB 时占 0.4%，可以忽略。

### 坑 B：单流数字不等于隧道能力

多数国内 CDN 对**单连接**有限速（常见 20–25 Mbps）。单流跑不满，不代表隧道不行。

**判断方法——加流数看总量：**

```powershell
# 单流
curl.exe -s -o NUL -w "%{speed_download}`n" <URL>
# 8 流并行，总量是否显著高于单流
```

| 现象 | 结论 |
| --- | --- |
| 8 流总量 ≈ 1 流 | 隧道到顶了 |
| 8 流总量 ≈ 8 × 1 流 | **源站按连接限速**，隧道还有余量 |
| 8 流总量介于两者之间 | 两边都在限制，需要换第二源站交叉验证 |

> **只测一个源站得出的"源站限速"是推断，不是证据。** 换第二个源站，单流仍卡在同样数字，才算证明。

### 坑 C：拿错测速目标

有些接口会**对代理流量判异常**（返回 403），测出来的不是链路性能。
还有些域名可能被规则导到了另一条线路上——那测的是别的隧道。

**要做的事**：测速前先确认这个目标**命中了你要测的那条线路**（见下面第三节的连接表方法）。

### 坑 D：不同时段混着比

同一条链路，一天之内质量会变。实测过的例子：

```
上午（网络刚恢复）：recv=27/30，丢 10%
下午（稳定后）：    recv=30/30，0 丢包，avg 225 ms
```

**丢包从 10% 变 0%，吞吐会直接翻倍。** 如果你的两次测量跨了时段，那比较的不是配置，是运气。

**铁律：一次实验内，所有对照必须同机、同时段、只改一个变量。**

### 坑 E：诊断命令本身给假阴性

**`Test-Connection` 在 PowerShell 5.1 里没有 `-DontFragment` 参数。**

参数不存在时它**不报错**，只返回空——看起来像"全部不通"。

```powershell
# ✗ 假阴性：不会报错，只会全 FAIL
Test-Connection -ComputerName <IP> -BufferSize 1400 -DontFragment

# ✓ 用 ping.exe
ping -n 3 -f -l 1400 <IP>
```

> 同理：**用 TCP 去探 QUIC 端口会得到假阴性。** `listen: :9443` 是 UDP，
> TCP 连不上才是正常的。要验证就测"能不能出网、出口是不是对端 IP"。

## 二、怎么判断一个吞吐数字可不可信

一条数字要可信，至少满足三条：

| 判据 | 怎么查 |
| --- | --- |
| **同机同时段** | 对照组和实验组在同一分钟级别内跑完 |
| **只改一个变量** | 声明值、端口、目标，一次只动一个 |
| **可重复** | 至少跑三次，取中位数；三次离散超过 10% 就不要下结论 |

**三次结果差得很大时**，先别归因于配置——大概率是：
链路波动（时段）、对端有别的程序占带宽、源站抖动。

## 三、怎么判断配置对不对：拐点法

`bandwidth.down` 是**硬上限**，不是建议值。设多少，Brutal 就按多少发。

**所以正确做法不是"调大试试"，是找拐点：**

```powershell
# 用 3 个声明值各测一次（每次改完要重启客户端）
# 8 / 10 / 12 mbps
curl.exe -s -m 90 -x socks5h://127.0.0.1:1081 -o NUL `
  -w "time=%{time_total}`n" "https://<测速目标>/20MB"
```

典型结果长这样（数值仅示意量级，你的环境会不同）：

| 声明 | 实测 | 占声明 |
| --- | --- | --- |
| 8 | ≈7.4 | ≈92% |
| 10 | ≈7.5 | ≈75% |
| 12 | **≈7.1** | ≈59% |

**判读规则：**

| 现象 | 含义 | 动作 |
| --- | --- | --- |
| 声明升高，实测**也升** | 还没到顶 | 继续加，直到不升 |
| 声明升高，实测**不升** | **到顶了** | 停在前一档 |
| 声明升高，实测**下降** | 超发，丢在瓶颈里 | **退回上一档** |

> 92% 不是损失。Brutal 按线上字节计（含 QUIC 头约 4%），而 `speed_download`
> 把 TTFB 也算进分母（约 4.5%），两项相乘正好 ~92%——**意思是足额送达**。

## 四、怎么判断"做成了"：五级验收

从便宜到贵，**每一级不过就不要往下走**。

### 第 1 级：端口在听

```powershell
Get-NetTCPConnection -State Listen -LocalPort 1081
```

不通过 → 客户端没起来，或端口被别的进程占了（见 pitfalls 坑 12）。

### 第 2 级：能出网，且出口是对端

```powershell
curl.exe -s -m 15 -x socks5h://127.0.0.1:1081 https://ipinfo.io/json
```

看 `ip` / `org` / `country`：
- 出口 = 对端的住宅 IP → ✅
- 出口 = 你的本地 IP → 代理没生效
- 出口 = 某个机房 → 规则把你导到别的线路上去了

### 第 3 级：实际走的是哪条路（别猜，读连接表）

```powershell
.\scripts\clashpipe.ps1 -Path '/connections' -OutFile conns.json
```

看每条连接的四个字段：`metadata.process` / `chains` / `rule` / `rulePayload`。

**这一步能抓出 90% 的"以为走了 A，其实走了 B"。**

### 第 4 级：环境一致性

目标是让**同一个页面里只出现一个出口身份**：

| 检查项 | 期望 |
| --- | --- |
| 浏览器出口 IP | 对端住宅 IP |
| Cloudflare 看到的 IP | **同上** |
| DNS 出口 | 对端 ISP 的 DNS |
| WebRTC UDP 出口 | 同上（做不到就接受，见 pitfalls 坑 10） |

**任何三项不一致，就说明流量没走同一个出口。**

### 第 5 级：稳定性和吞吐

```powershell
# 30 包看丢包和抖动
ping -n 30 <对端 IP>
# 单流 20 MB 看拐点
```

| 指标 | 可用 | 勉强 | 不可用 |
| --- | --- | --- | --- |
| 丢包 | < 2% | 2–10% | > 15% |
| 抖动（stdev） | < 10 ms | 10–40 ms | > 60 ms |
| RTT | < 200 ms | 200–350 ms | > 400 ms |

## 五、怎么判断问题在"环境"还是在"配置"

这是最省时间的一条判据：

| 现象 | 更可能是 |
| --- | --- |
| 同一份配置，昨天好今天坏 | **环境**（链路、对端、上游拥塞） |
| 只改一个变量，数字**完全不动** | 瓶颈**不在**你改的那一层 |
| 所有目标都慢，但 ICMP 正常 | 大包路径有问题（MTU）或对端出口拥塞 |
| ICMP 正常、TCP 塌、QUIC 正常 | **典型的高 RTT + 丢包链路**，这是 Brutal 的存在理由 |
| 端口在听、服务端零日志、客户端一直超时 | 防火墙 Block 压过 Allow（坑 7） |

**记住一句**：**"改了没变化"是最有价值的信息**——它直接排除了你改的那一层，
比"改了有变化"信息量更大。
