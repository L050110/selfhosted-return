# 用一台境内的家用电脑做回国出口

**政务网站 11 秒超时打不开 → 0.61 秒。成本零。**

**方向的唯一正确读法**：使用者在**境外**，出口在**境内**。
服务端装在**境内**那台（它的住宅 IP 就是出口），客户端装在**境外**这台。
这篇文章讲的就是：怎么把境内亲友家的一台普通电脑，变成一个只给你用的回国出口。

这篇文章讲一套自建的回国加速方案：两端都是普通家用宽带，一台在境内、一台在境外，
不租服务器、不买专线、不走商业加速器。完整的部署脚本和踩坑记录开源在文末的仓库里。

---

## 先说清楚它解决什么问题

很多人有这样的经历：人在境外，要访问境内的政务门户、企业信用查询、票务、银行。
这些站点和其他"需要翻出去"的站不一样：

```
· 它们不是"被墙"，是本来就在境内
· 境外直连能到，但慢，而且部分站点会卡在 JS 挑战上等到超时
· 商业加速器的机房 IP 经常被这些站点额外风控
```

**最后一条是关键：住宅 IP 和机房 IP 在这些站点眼里不是一回事。**

这也是为什么「自己搭」在这里有实际意义——不是为了省钱，是为了拿到一个住宅 IP 的出口。

## 实测数据

同一台机器、同一时段，`curl -w "%{http_code} %{time_total}"` 直连 vs 走隧道：

| 目标 | 直连 | 走隧道 |
|---|---|---|
| 政务门户（带 JS 挑战） | **11.2 秒超时，打不开** | **0.61 秒**（连测三次：0.61 / 0.63 / 0.61） |
| 政务子站（安全监管平台） | 打不开 | **0.26 秒** |
| 企业信息查询 | 1.16 秒 | **0.55 秒** |
| 地方政务 | 打不开 | **0.34 秒** |
| 视频站 | 0.80 秒 | **0.62 秒** |
| 普通搜索引擎 | 0.80 秒 | 0.74 秒 |

链路本身：

```
RTT（20 包 ICMP）      306 ms，0% 丢包
Tailscale 层 RTT       209 ms
隧道纯能力（内置测速）  99.4 Mbps 单流
经真实源站            21 Mbps 单流 / 85 Mbps 并行
```

**注意最后两行的差距：单流只有 21，但隧道能跑 99。这不是隧道的问题，
是多数境内 CDN 对单连接限速 20–25 Mbps。视频站和浏览器会自动开多连接，所以体感远好于单流数字。**

## 架构：四个组件，各管一件事

```
┌──────────────┐                    ┌──────────────┐              ┌──────────┐
│  境外这一端   │                    │  境内那一端   │              │ 目标站点  │
├──────────────┤                    ├──────────────┤              ├──────────┤
│ 浏览器/应用   │                    │              │              │          │
│   ↓ 系统代理  │                    │              │              │          │
│ 本地代理内核  │  只把需要的流量    │              │              │          │
│ （分流规则）  │ ────────────────▶ │              │ ───────────▶ │          │
│ hysteria2    │   QUIC over        │  hysteria2   │  普通 TCP    │          │
│  客户端       │   Tailscale        │   服务端     │              │          │
│ Tailscale    │                    │ Tailscale    │              │          │
└──────────────┘                    └──────────────┘              └──────────┘
```

| 层 | 组件 | 解决什么 | 换掉会怎样 |
|---|---|---|---|
| 连通 | Tailscale | 两台都在 NAT 后的机器怎么互访 | 要自己搞端口映射、DDNS、证书 |
| 传输 | hysteria2 | 跨境链路丢包时 TCP 会崩 | 高丢包下吞吐掉到个位数 |
| 分流 | 本地代理内核 | 哪些流量进隧道 | 全走隧道拖慢本地访问 |
| 守护 | 看门狗 | 进程崩了自动回来 | 崩一次断到下次开机 |

### 为什么是 hysteria2 而不是普通 WireGuard

**跨境链路的关键变量是丢包，不是带宽。**

公开的第三方实测（不是我的数据）：

```
25% 丢包：TUIC 6.6–7.3 Mbps，Reno QUIC 完全不可用
1–3% 丢包：Hysteria2 90 Mbps > TUIC 77 Mbps
```

hysteria2 的 Brutal 是**固定速率发送**：不探测、不退缩，按你设定的速率硬发。
在高丢包的跨境链路上，这比 BBR 那种"探测到丢包就退让"的策略有效得多。

**代价是它不聪明**——设多少就发多少，设错了就是持续丢包。这是后面坑 2 的由来。

## 天花板在哪：三样相乘

这是最多人误解的地方。**软件优化只能动第三项，前两项是钱和地理。**

```
实际吞吐 ≈ 对端上行带宽 × 跨境链路效率 × 协议栈效率
              ↑宽带套餐      ↑运营商路由      ↑软件可优化（5–15%）
```

### 第一项：对端的上行带宽

**你「下载」时，数据是对端「上传」给你的。所以决定你下载速度的是对端的上行。**

多数家用宽带上行远小于下行：

| 套餐 | 典型下行 | 典型上行 | 你能拿到的上限 |
|---|---|---|---|
| 100M | 100 Mbps | 20–30 Mbps | 20–30 Mbps |
| 300M | 300 Mbps | 30–50 Mbps | 30–50 Mbps |
| 500M | 500 Mbps | 50–100 Mbps | 50–100 Mbps |
| 1000M | 1000 Mbps | 100–200 Mbps | 100–200 Mbps |

> 上表上行档位是行业常见值，不是实测。你所在地以运营商合同为准，
> 务必先跑一次 `hysteria speedtest` 测真实值再规划。

**本项目实测对端上行 99.4 Mbps，跨境跑出 85 Mbps。85 / 99.4 = 86%。**

### 第二项：跨境链路效率

| 线路 | 典型 RTT | 典型丢包 | 效率 | 月费量级 |
|---|---|---|---|---|
| 普通家宽 | 180–320 ms | 0.1–1% | **60–86%** | 免费 |
| 运营商优化（CN2 GT 等） | 150–200 ms | 0.05–0.3% | 80–90% | 免费～几十 |
| CN2 GIA / IPLC 专线 | 130–180 ms | < 0.01% | 90–98% | 几百到几千 |

> 除「普通家宽」一行外，其余是行业公开经验的典型值，非实测。采购前要服务商给测试 IP 自己验。

**家宽会损失 14–40%，来自四处：**

```
① 封装开销：QUIC 头 + WireGuard 头，每包多 60–80 字节
② 路由绕行：家用宽带的国际出口不一定走最短路径
③ 拥塞丢包：民用出口是共享的，晚高峰劣化
④ 对端 NAT：打洞失败退到中继，效率再掉一半
```

### 第三项：协议栈效率（唯一能靠调参动的）

| 优化点 | 效果 |
|---|---|
| 修 MTU（下面那个坑） | 从「完全不通」到「能通」 |
| 固定速率设对值 | 5–25% |
| 减少中间层（PAC → 内核规则） | 5–20% |
| 避开本地内核劫持隧道进程 | 10–50% |
| 多连接并行 | 2–4 倍（但受前两项封顶） |

**三项叠起来：99.4 × 86% = 85.5，实测 85。吻合。**

### 延迟是另一条独立的墙

```
跨洲际链路，光纤中的光速往返就有约 130 ms
加路由器跳转和海底光缆绕行，200–320 ms 是常态
CN2 GIA 能压到 150–180，再低是物理不可能
```

**所以「做到和境内一样」在物理上不成立。** 能做到的是「从打不开变成 0.6 秒打开」，
那个差别用户能感觉到；0.6 秒和 0.3 秒的差别，用户感觉不到。

## 九个坑，每个都会让你以为「这套东西不能用」

### 坑 1：MTU 差 28 字节，而且失败是静默的

```
症状：客户端报 timeout: no recent network activity
      服务端日志完全没有连接记录
      抓包抓不到任何相关包
      从本机回环连同一个服务端：完全正常
```

这组症状会让人往防火墙、端口、认证方向查，**全是错的方向**。

根因：

```
quic-go 的 InitialPacketSize 默认 1280 字节（UDP 载荷）
+ IPv4 头 20 + UDP 头 8 = 1308 字节的 IP 包
而虚拟网卡 MTU 1280 只允许 1252 字节载荷（1280 - 28）

差 28 字节
```

**为什么静默：** quic-go 把 `EMSGSIZE` 当可忽略错误（设计上留给 Path MTU Discovery），
但握手阶段 PMTUD 还没启动，所以每个 Initial 包都发不出去，却按 PTO 定时器原样重传。
客户端只看到超时，服务端什么都没收到。

修法：把虚拟网卡 MTU 提到 1320 以上（IPv4 需 1308，兼顾 IPv6 需 1328）。

**这个坑值得单独立一节，因为：**

```
· Tailscale 的相关 issue 从 2021 年开到现在还没定论
· 上游 quic-go 只修了「本机发送报错」这一种
  路径中间某跳 MTU 1280、服务端回包方向，都还没修
· 差额 28 字节，靠算术能推但极难想到
```

### 坑 2：`bandwidth.down` 是硬上限

Brutal 是固定速率发送，设 40 就发 40，不是"最多 40"。

```
实测同一条链路：
  down=40  → 单流 21.3 / 4 流 35.9
  down=80  → 单流 22.5 / 4 流 71.2
  down=120 → 单流 22.9 / 4 流 86.7   ← 饱和
  down=200 → 单流 22.9 / 4 流 86.2   ← 不再增长
```

120 和 200 结果一样，说明 86.7 就是链路真实上限。
**正确做法：设成实测能力的 90–95%。设太高会持续丢包重传，实际更慢。**

### 坑 3：`ignoreClientBandwidth: true` 让 Brutal 失效

服务端配置里如果有这一行，它会忽略客户端的带宽声明，回落成 BBR。
**BBR 在高丢包跨境链路上表现远差于固定速率发送。** 而且这行不会报错，只是悄悄变慢。

### 坑 4：Windows 上 `netsh` 改的 MTU 会被覆盖

虚拟网卡的 MTU 由创建它的服务决定，服务重启时会重新配置接口。
外部改的值只能维持到下次重启。

Tailscale 在 Windows 上读 `C:\ProgramData\Tailscale\tailscaled-env.txt` 里的环境变量：

```
TS_DEBUG_MTU=1320
```

并且要清掉机器级的同名环境变量（两个来源会打架）。

### 坑 5：本地代理内核劫持了隧道进程

本机装着 Clash / mihomo 且开了 TUN 模式时，隧道进程自己发出的流量也会被 TUN 接管，
按规则可能落到「走机场节点」——于是绕到境外再回境内，速度废掉。

**实测：加规则前 8 流只有 40–72 Mbps 且不稳，加规则后稳定 85。**

修法是在规则最前面加：

```yaml
rules:
  - PROCESS-NAME,hysteria.exe,DIRECT
  - PROCESS-NAME,mihomo.exe,DIRECT
```

### 坑 6：`tls.sni` 填了 IP，报一个看不懂的错

```
FATAL failed to initialize client
{"error": "connect error: CRYPTO_ERROR 0x150 (remote): tls: internal error"}
```

看起来像证书或密码问题，**两个都不是**。

RFC 6066 规定 TLS 的 SNI 扩展只能是 DNS 主机名，不能是 IP 字面量。
收到 IP 形式的 SNI，Go 的 `crypto/tls` 直接失败，错误码 `0x150 = internal_error`。
而 `insecure: true` 只关掉证书链验证，不会让非法的 SNI 变合法。

修法：`sni` 必须是域名形式，**而且必须等于服务端证书的 CN**。

> 这条我一开始写错了，实测打回来：`insecure: true` 只跳过**证书链校验**，
> SNI 的格式和匹配仍然会被检查。填一个「随便的占位域名」照样握手失败。
>
> 更麻烦的是 hysteria 2.x 的 `cert` 子命令**不吃任何参数**——
> `hysteria cert --host my.domain` 直接 `FATAL cert command does not accept arguments`。
> 它用 `os.Hostname()` 当 CN。所以正确流程是：
> 先 `hysteria cert`，再读出 CN，再把客户端的 `sni` 对齐过去。
> `scripts/setup-server.ps1` 会把 CN 写进 `cert-cn.txt`，
> `setup-client.ps1` 读它——读不到就拒绝生成配置，而不是瞎填一个。

### 坑 7：防火墙里一条指名的 `Block` 规则压过 `Allow`

```
症状：端口在听，进程在跑，服务端日志一条没有
      客户端一直 timeout: no recent network activity
      换个端口还是 timeout，关掉防火墙就好了
```

Windows 防火墙不是「有 Allow 就放行」。**任何一条显式 `Block` 命中就直接丢包**，
后面的 `Allow` 根本不会被评估。装过几个代理工具之后很容易留下这种孤儿规则，
端口写的是 `Any`，UDP/TCP 全封。

修法：把指向隧道程序的 Block 规则删掉。`scripts/verify.ps1` 的 P7 会替你查。

### 坑 8：SSH 里起的进程会跟着会话一起死

远程起服务、断开 SSH、三十秒后进程没了，**没有任何退出日志**。
`conhost --headless`、`-WindowStyle Hidden` 都救不了——会话结束时会关掉整个 job object。

修法：让进程的父级不是你的 SSH 会话。用计划任务（`AtLogOn` + 每 5 分钟），
脚本自己判断进程在不在，就是最朴素的看门狗。

顺带一个坑：`schtasks /delete` 只删任务，**不会杀掉已经在跑的进程**。

### 坑 9：用 TCP 探 QUIC 的端口，得到假阴性

`Test-NetConnection -Port 9443` 返回 False，于是判断「服务端没起」，
去改防火墙、改端口、换机器，全白费。

`listen: :9443` 是 **UDP/QUIC**，那个端口上根本没有 TCP listener，
所以 TCP 连不上是**正确行为**。

修法：别探端口，直接测端到端——能不能出网、出口是不是对端的 IP：

```powershell
curl.exe -s --socks5-hostname 127.0.0.1:1081 https://ipinfo.io/json
```

DNS、QUIC 握手、Brutal、NAT、防火墙，任何一环坏了它都会失败。

## 部署：新旧并存，切换只改一个注册表值

这是整套流程里最重要的设计决定。

**不要一步换掉旧方案。让新旧同时跑，PAC 写多级回退：**

```javascript
// 需要走隧道的域名：新内核 → 旧客户端 → 直连
return "PROXY 127.0.0.1:7890; PROXY 127.0.0.1:10809; DIRECT";

// 其余域名：新内核 → 直连（故意不回退到旧的，避免把境外站送进隧道）
return "PROXY 127.0.0.1:7890; DIRECT";
```

浏览器在**代理端口连不上**时自动尝试下一个。本机端口没人监听会立即被拒绝，
回退几乎无延迟。所以新内核起不来时，行为自动退回旧状态。

**它管不了的情况：进程活着但隧道断了。** 这时浏览器认为代理正常，不会回退——
这种情况只能靠观察日志和手动回滚。

切换用**新文件名 + 改注册表**，绝不原地改 PAC 内容：

```
PAC 有缓存。原地改内容，浏览器可能不重读，要等重启或几小时后。
后果是你以为切过去了，其实浏览器还在用旧脚本，
观察到的现象和操作对不上，排查方向直接错掉。
```

回滚就是一条命令：

```powershell
Set-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings" `
    -Name AutoConfigURL -Value "file:///C:/Users/<user>/old.pac" -Force
```

## 它不适合谁

**诚实地列出来：**

```
❌ 对方电脑不能长期开机        通道随时断，体验比商业方案差
❌ 你和对方不熟                装软件、调参、排查都要沟通，关系不够很难受
❌ 你需要 7×24 可用            这套做不到，一端关机或重启就断
❌ 你只是想看视频刷社交        商业加速器更省事
❌ 链路丢包低于 0.5%           hysteria2 优势发挥不出来
❌ 你不想折腾                  九个坑足够让不熟悉的用户放弃三次
```

**适合：**

```
✅ 需要访问对机房 IP 有额外风控的站点
✅ 境外有信任的人，且对方机器能长期开着
✅ 愿意花半天部署，能自己排查
✅ 对数据不经第三方有要求
```

## 一个必须说清楚的前提

**这套方案的可用性完全绑定在对方那台机器上。**

```
对方关机          → 立刻断
对方重启装更新    → 断几分钟到几小时
对方网络故障      → 断
对方拔电源        → 断，且你无法恢复
```

**本项目实测里就撞过一次：对方机器因为 Windows 自动更新重启，随后进入睡眠，
通道断了 2.5 小时，正好在对方使用时段。**

所以部署时要一并处理：

```
· Windows 更新的活动时间要避开设为「对方活跃时段」
· 关闭自动睡眠/休眠
· 计划任务设开机自启 + 崩溃自动重启
· 真正的解法是换成一个不会动的设备（迷你主机/树莓派）
```

**最后一条是关键。把「住宅 IP 出口」从一台会关机的笔记本，变成一个固定设施——
这才叫可用性。**

## 最后

这套东西的前提是「有个在境外的人愿意帮你」。这一条软件解决不了。

所以它的定位是：**给已经有这个前提的人，一套能落地的方法。**

如果你没有那个前提，商业加速器是更现实的选择——这不是客套话，
是这套方案在「可用性」和「省心程度」上确实不如商业产品，它换来的只有一样东西：

**一个住宅 IP 的出口，以及数据只经过你们两台机器。**
