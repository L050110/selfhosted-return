# 为什么这么选

**这套方案由三个组件组成，每个解决一个特定问题。任何一个换掉都会让整体退化。先说清取舍，你就知道自己该不该用这套。**

---

## 整体架构

```
┌─────────────┐         ┌─────────────┐         ┌──────────────┐
│  你的机器    │         │  对方的机器  │         │  目标站点     │
│  （境外侧）  │         │  （境内侧）  │         │              │
├─────────────┤         ├─────────────┤         ├──────────────┤
│ 浏览器/应用  │         │             │         │              │
│   ↓ 系统代理 │         │             │         │              │
│ 本地代理内核  │         │             │         │              │
│ （分流规则）  │         │             │         │              │
│   ↓ 只把需要 │         │             │         │              │
│     的流量   │         │             │         │              │
│ hysteria2   │────────▶│ hysteria2   │────────▶│  国内站点     │
│  客户端      │  QUIC   │  服务端      │  普通   │              │
│             │  over   │             │  TCP    │              │
│ Tailscale   │  Tail-  │ Tailscale   │         │              │
│  （打洞）    │  scale  │  （打洞）    │         │              │
└─────────────┘         └─────────────┘         └──────────────┘
```

**四个层次，各管一件事：**

| 层 | 组件 | 管什么 | 换掉会怎样 |
|---|---|---|---|
| 1. 连通 | Tailscale | 让两台在 NAT 后的机器能互访，自动打洞 | 要自己搞端口映射、DDNS、证书 |
| 2. 传输 | hysteria2 | 跨境数据传输，抗丢包 | TCP 类协议在高丢包下会崩 |
| 3. 分流 | 本地代理内核 | 决定哪些流量进隧道 | 全部走隧道会拖慢本地访问 |
| 4. 守护 | 看门狗 | 崩溃自动重启 | 崩一次断到下次开机 |

---

## 组件一：Tailscale（为什么不用裸 WireGuard）

**它解决的是「两台机器都在 NAT 后面，怎么连上」。**

| 方案 | 需要什么 | 打洞成功率 | 维护成本 |
|---|---|---|---|
| **Tailscale** | 装个客户端，登录 | 高（有 DERP 中继兜底） | 零 |
| 裸 WireGuard | 一端要有公网 IP 或端口映射 | 取决于 NAT 类型 | 要维护 DDNS、证书、防火墙 |
| frp / ngrok | 一台有公网 IP 的中转 | 100%（但要中转） | 要租服务器 |

**选它的理由：**

```
· 两端的 NAT 都不确定，Tailscale 的 DERP 兜底能保证「至少能通」
· 不依赖对方懂技术（装完登录就行）
· 免费额度够两个人用
· 加密和密钥管理不用自己搞
```

**它的代价：**

```
· MTU 默认 1280，会触发坑 1（这是本仓库最大的技术门槛）
· 走中继时速度会掉一半以上（DERP 是 TCP）
· 依赖它自己的控制平面（挂了就断）
```

**替代方案**：如果两端都有公网 IP（比如一端是 VPS），直接 WireGuard 更简单，也不会有 1280 的坑。

## 组件二：hysteria2（为什么不用 TCP）

**它解决的是「跨境链路丢包时，TCP 类协议吞吐会崩」。**

| 协议 | 高丢包（3%+）下的表现 | 说明 |
|---|---|---|
| 原生 TCP | 严重退化 | 拥塞窗口被丢包打回，RTO 翻倍 |
| TCP + BBR | 中等退化 | 比 CUBIC 好，但仍受丢包影响 |
| **hysteria2（QUIC + 固定速率）** | **几乎不受影响** | 不探测，按设定速率硬发 |
| TUIC（QUIC + BBR） | 中等 | QUIC 承载，但拥塞控制是 BBR |

**公开的实测数据**（第三方在真实跨境链路上测的，非本项目）：

```
25% 丢包：TUIC 6.6-7.3 Mbps，Reno QUIC 完全不可用
1-3% 丢包：Hysteria2 90 Mbps > TUIC 77 Mbps
```

**所以：丢包越高，hysteria2 优势越大；链路干净时，它反而不如 BBR 类协议。**

**它的代价：**

```
· 固定速率发送意味着「设多少发多少」，设错就是持续丢包（坑 2）
· 服务端和客户端都要支持它（生态不如 TCP 广）
· 部分网络对 UDP 有 QoS 或限制
```

**替代方案**：链路丢包低于 0.5% 时，TUIC 或 VLESS+Vision 更省心。

## 组件三：本地代理内核（为什么不直接用 PAC）

**它解决的是「哪些流量该进隧道」。**

| 方案 | 覆盖率 | 性能 | 门槛 |
|---|---|---|---|
| 手写 PAC 域名列表 | 低（靠猜，漏一个那个站就打不开） | 中（有 JS 判断开销） | 低 |
| **内核规则集（GEOSITE/GEOIP）** | **高（十几万条）** | **高（内核层匹配）** | 中 |
| 全局代理 | 100% | 低（本地流量也绕一圈） | 最低 |

**为什么手写 PAC 不够：**

```
· 国内站点有几十万个，你只能猜常用的那几十个
· 漏掉的站点会直连 → 打不开 → 用户不会报「这个没走代理」，
  只会说「打不开」，于是你以为整套方案坏了
· 有些站点域名在国内 CDN 上，但域名后缀看不出归属
```

**内核规则集的价值就在这：它按「站点归属」而不是「域名后缀」分类。**

## 组件四：看门狗（为什么必须有）

**它解决的是「进程崩了不会自己回来」。**

```
开机自启 ≠ 崩溃自动重启

Windows 上「开机启动」的几种做法各有失效场景：
  · 启动文件夹快捷方式   崩了不会重启
  · 注册表 Run 键        同上
  · 计划任务 + 最高权限   交互式登录时会静默失败（LastTaskResult=1）
  · 从 SSH 启动进程      SSH 断开会杀掉进程

本项目用的组合：
  看门狗循环脚本 + 计划任务（普通权限、每 5 分钟触发、已在运行则忽略）
```

**实测效果：杀掉进程后 14-16 秒自动恢复。** 详见 [deploy.md](deploy.md)。

## 和商业方案的完整对比

| 维度 | 商业加速器 | 机场 | 自建 VPS 中转 | **本方案** |
|---|---|---|---|---|
| 出口 IP | 机房 | 机房 | 机房 | **住宅** |
| 带宽 | 共享 | 共享 | 独享但看套餐 | **独享（对方家的宽带）** |
| 延迟 | 150-250ms | 150-300ms | 150-200ms | **180-320ms** |
| 政务/银行类 | 部分被拒 | 常被拒 | 常被拒 | **正常** |
| 费用 | 月付 | 月付 | 月付 + 流量 | **零（电费除外）** |
| 可用性 | 7×24 | 7×24 | 7×24 | **依赖对方开机** |
| 出问题 | 有客服 | 有客服 | 自己查 | **自己查** |
| 部署成本 | 零 | 零 | 半天 | **半天到一天** |
| 数据路径 | 过服务商 | 过服务商 | 过自己的 VPS | **只过两台自己的机器** |

**总结成一句话：**

```
本方案用「可用性」和「省心程度」换「住宅 IP + 零成本 + 数据私密」。

如果你更需要可用性，用商业方案。
如果你需要住宅 IP 才能访问某些站点，这是少数可行的办法之一。
```

## 什么时候不该用这套

**诚实地列出不适合的场景：**

```
❌ 对方电脑不能长期开机
   → 通道随时断，体验比商业方案差得多

❌ 你和对方不熟
   → 装软件、调参数、出问题排查都需要沟通，关系不够会很难受

❌ 你需要 7×24 可用
   → 这套方案做不到，一端关机或重启就断

❌ 你只是想看视频/刷社交媒体
   → 商业加速器更省事，成本也更低

❌ 链路丢包率低于 0.5%
   → hysteria2 的优势发挥不出来，普通 WireGuard 更简单

❌ 你不想折腾
   → 这套方案的坑足够让一个不熟悉的用户放弃三次
```

**适合的场景：**

```
✅ 你需要访问对「机房 IP」有额外风控的站点
✅ 你在境外有信任的人，且对方的机器能长期开着
✅ 你愿意花半天时间部署，而且能自己排查问题
✅ 你对数据不经第三方有要求
```

## 一个必要的提醒

**这套方案的可用性完全绑定在对方那台机器上。**

```
对方关机          → 立刻断
对方重启装更新    → 断几分钟到几小时
对方网络故障      → 断
对方拔掉电源      → 断，且你无法恢复
```

**本项目的实测里就遇到过：对方机器因为 Windows 自动更新重启，
随后进入睡眠，导致通道断了 2.5 小时，正好撞在使用时段。**

**所以部署时要一并处理：**

```
· Windows 更新的活动时间避开对方的使用时段（见 deploy.md）
· 关闭自动睡眠/休眠
· 计划任务设为开机自启
· 如果条件允许，用一个常开的小设备（迷你主机/树莓派）代替笔记本
```

**最后一条是真正的解法：把「住宅 IP 出口」从一台会关机的笔记本，
变成一个不会动的固定设施。这一点在 README 的前提条件里已经写明。**
