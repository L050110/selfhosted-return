# 理论上限：什么决定了你能跑多快

**一句话：上限由三样相乘，软件只能优化第三项，前两项是钱和地理。**

```
实际吞吐 ≈ 对端上行带宽  ×  跨境链路效率  ×  协议栈效率
              ↑                ↑                ↑
          宽带套餐决定      运营商路由决定    软件可优化
```

---

## 第一项：对端上行带宽（最大的一道墙）

**关键认知：你「下载」时，数据是「对端」上传给你的。所以决定你下载速度的，是对端的上行带宽，不是你自己家的下行。**

多数家用宽带是「下行远大于上行」的非对称套餐：

> ⚠️ **下表的上行档位是行业常见值，不是本项目实测。**
> 你所在地的实际配置以运营商合同为准，务必先用 `hysteria speedtest` 测出真实上行再规划。

| 套餐档位 | 典型下行 | 典型上行（行业常见值，需自行核实） | 你能拿到的单流速度上限 |
|---|---|---|---|
| 100M | 100 Mbps | 20–30 Mbps | 20–30 Mbps |
| 200M | 200 Mbps | 30–50 Mbps | 30–50 Mbps |
| 300M | 300 Mbps | 30–50 Mbps | 30–50 Mbps |
| 500M | 500 Mbps | 50–100 Mbps | 50–100 Mbps |
| **1000M（对称或上行 100）** | 1000 Mbps | **100–200 Mbps** | **100–200 Mbps** |

**实测对照**：本项目测到的对端上行是 **99.4 Mbps**（用 hysteria 内置测速，不经任何源站），
之后跨境跑出 **85 Mbps**——85 / 99.4 = 86%。

**所以第一步永远是：先测对端的上行，那是天花板。**

```powershell
# 在对端机器上，用内置测速（不经源站，测的是纯隧道能力）
hysteria.exe speedtest -c client.yaml

# 或者用公开测速站，但要注意它可能被限速
```

**如果对端上行只有 30 Mbps，那么无论怎么调软件，你的下载都不会超过 30。**

---

## 第二项：跨境链路效率（运营商和地理决定）

**这一项完全不受软件控制，只能靠换线路改变。**

> ⚠️ **下表除「普通家宽」一行外，其余三行的 RTT、丢包、月费都是行业公开经验的典型值，
> 不是本项目实测。** 本项目只实测了「普通家宽」这一行（见下方实测段落）。
> 采购前请要求服务商提供测试 IP 自行验证。

| 线路类型 | 典型 RTT | 典型丢包 | 跨境效率 | 月费量级 |
|---|---|---|---|---|
| **普通家宽**（移动/联通/电信国际出口） | **180–320 ms** ✅实测 | **0.1–1%** | **60–86%** ✅实测 | 免费（已包含在宽带里） |
| 运营商优化线路（CN2 GT / 联通 9929） | 150–200 ms | 0.05–0.3% | 80–90% | 免费～几十 |
| **CN2 GIA / IPLC 专线** | **130–180 ms** | **< 0.01%** | **90–98%** | **几百到几千** |
| 云厂商跨区内网（如阿里云香港到内地） | 30–60 ms | 极低 | 95%+ | 按流量计费 |

**本项目实测的「普通家宽」具体数字：**

```
Tailscale ping 实测    209 ms      （WireGuard 层的往返）
裸 ICMP 实测           306 ms      （20 个包，0% 丢包）
上线实测               99.4 Mbps   （hysteria speedtest 单流）
跨境实跑               85 Mbps     （4 流饱和）
效率                   85 / 99.4 = 86%
```

**注意 86% 已经落在上表「普通家宽 60–86%」的最优端，说明这条链路的运营商路由还可以，
继续优化的空间不大。多数人测出来会在 60–75%。**

**关键：本项目测到的 86% 效率（99.4 → 85）是普通家宽的正常水平。**

**想往上走的唯一办法是换线路，而那是运营商收月租的东西，不是配置能改的。**

### 为什么家宽会损失一部分（本项目实测 14%，经验区间 15–40%）

```
① 封装开销：QUIC 头 + WireGuard 头，每个包多 60–80 字节
   按 1320 字节的包算，光头部就吃掉 5–6%

② 路由绕行：家用宽带的国际出口不一定走最短路径
   同一城市不同运营商，RTT 可能差 100 ms

③ 拥塞与丢包：民用出口是共享的，晚高峰会劣化
   丢包 0.5% 时，TCP 类协议吞吐会掉 30% 以上
   （QUIC + 固定速率拥塞控制能缓解，但不能消除）

④ 对端 NAT：如果打洞失败退到中继，效率会再掉一半以上
```

## 第三项：协议栈效率（软件能优化的部分）

这一项是唯一能靠调参改善的，但收益也就 5–15%。

| 优化点 | 效果 | 说明 |
|---|---|---|
| 修 MTU（1308 那个坑） | **从「完全不通」到「能通」** | 不是提速，是让功能成立 |
| 固定速率拥塞控制设对值 | 5–25% | 设太高会持续丢包，设太低跑不满 |
| 减少中间层（PAC → 内核规则） | 5–20% | 少了 JS 判断和二次转发 |
| 避开本地代理内核的劫持 | 10–50% | 隧道进程被 TUN 抓走会绕远路 |
| 多连接并行 | 2–4 倍（相对单流） | 但受第一项和第二项封顶 |

**注意最后一行：多连接能让总量接近链路上限，但不能突破它。**

## 实测：三层怎么叠加

```
对端上行            99.4 Mbps     ← 第一项，宽带套餐决定
跨境效率            86%           ← 第二项，运营商路由决定
                                 ─────────────
理论上限            85.5 Mbps     ← 实测 85 Mbps，吻合
协议栈开销          已包含在上面的 86% 里
```

**再看单流为什么只有 21 Mbps：**

```
85 Mbps（链路能力） ÷ 4 条连接 = 21.25 Mbps/条
```

**那 4 条连接各自被源站限到 21–24 Mbps，加起来正好 85。**
**所以单流的 21 不是隧道的问题，是源站按连接限速。**

**证据**：同一源站，用 8 条连接并行，总量还是 85（不再涨）；
而用 hysteria 内置测速（不经源站）单流就能到 99.4。

## 结论：你的天花板在哪

```
先测这三样：
  ① 对端上行     ← 决定你的绝对上限
  ② 两点间 RTT    ← 决定首屏延迟（打不开的地方主要卡这个）
  ③ 对端到目标的单连接速度  ← 决定单流体验

如果 ① 只有 30 Mbps：
  软件优化到极致也就是 25-28 Mbps，别再折腾

如果 ① 有 100 Mbps 但只跑出 40：
  检查第二项（是不是走了中继、是不是绕路）

如果 ① 有 100 Mbps 且跑出 85：
  已经到 86%，正常。想再快要换线路或升级套餐
```

## 延迟：另一条独立的墙

**吞吐可以靠带宽堆，延迟不能。**

```
跨洲际链路，物理光速往返就有 130 ms 左右
加上路由器跳转、海底光缆绕行，200–320 ms 是常态
CN2 GIA 能压到 150–180，再低就是物理不可能
```

**延迟决定的是「首屏要等多久」，不是「能跑多快」：**

```
首屏时间 ≈ 3 个 RTT（DNS + TCP + TLS）+ 服务端处理时间

RTT 209 ms  →  首屏 0.6–0.8 秒   （本项目实测 0.26–0.74）
RTT 306 ms  →  首屏 0.9–1.2 秒
RTT 150 ms  →  首屏 0.5–0.6 秒
RTT 30 ms   →  首屏 0.1–0.2 秒   （国内本地的水平）
```

**所以「做到和国内一样」在物理上不成立。能做到的是「从打不开变成 0.6 秒打开」，那个差别用户能感觉到；0.6 秒和 0.3 秒的差别，用户感觉不到。**
