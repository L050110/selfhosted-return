# 用一台境内的家用电脑做回国出口

> 国内网站打开要十几秒、政务站点直接超时、视频一直在缓冲？
> 如果你在境内有个能长期开机的亲友，那台机器就能做你的回国出口——
> 目标站点做到 **0.3–0.7 秒打开**，成本接近零（不含电费）。

> **方向的唯一正确读法**：使用者在**境外**，出口在**境内**。
> 服务端装在**境内**那台（它的住宅 IP 就是出口），客户端装在**境外**这台。
> 装反了整套方案不成立——境外出口对「访问境内网站」没有任何帮助。

## 实测数据

两台**家用宽带**，跨洲际链路，Tailscale 直连 + hysteria2。
下表是同一个站点在同一台机器上，**直连 vs 走隧道**的对比：

| 目标站点类型 | 直连 | 走隧道 |
|---|---|---|
| 政务门户（含 JS 挑战） | **11.2 秒超时，打不开** | **0.61 秒**（连测三次：0.61 / 0.63 / 0.61） |
| 政务子站（安全监管平台） | 打不开 | **0.26 秒** |
| 企业信息查询 | 1.16 秒 | **0.55 秒** |
| 地方政务 | 打不开 | **0.34 秒** |
| 视频站 | 0.80 秒 | **0.62 秒** |
| 普通搜索引擎 | 0.80 秒 | 0.74 秒 |

> 表中所有数字都是同一台机器、同一时段实测，方法是 `curl -w "%{http_code} %{time_total}"`
> 对比 `--noproxy`（直连）和 `-x http://127.0.0.1:<本地代理端口>`（走隧道）。
> 政务类站点的「打不开」表现为 HTTP 000 + 11 秒左右的超时。

吞吐（同一隧道，不同源站）：

| 场景 | 数值 |
|---|---|
| 隧道纯能力（不经源站） | **99.4 Mbps** 单流 |
| 经真实源站 | 21 Mbps 单流 / 85 Mbps 并行 |
| 单流上限的来源 | **源站按连接限速**，不是隧道 |

> 单流只有 21 Mbps 是因为多数国内 CDN 对单连接限速 20–25 Mbps，
> 隧道本身单流能跑 99 Mbps。视频站、浏览器会自动开多连接，所以实际体验远好于单流数字。

**理论上限见 [docs/performance.md](docs/performance.md)** ——
一句话：取决于国内那端的上行带宽和是否走专线，不是软件能突破的。

## 前提条件（这条绕不过去）

```
1. 境内那一端要有人，而且要愿意帮你
2. 那台机器要能长期开机（关机 = 你这边立刻断）
3. 两端都要装软件、要配对、要调参数
4. 出问题只能你自己查，对面大概率不懂技术
```

**关键：境内那台机器的住宅 IP，就是这个方案的出口。** 这也是它和商业加速器的
根本区别——不是省钱，是拿到一个「境内住宅」的出口。

**这不是一个软件，是一套方案。本仓库不提供任何可用节点、订阅链接或服务端。**

所有脚本都要求你自己填两端的地址，仓库里没有任何默认值。

## 它和商业加速器有什么不同

| | 商业加速器 | 本方案 |
|---|---|---|
| 出口 IP 类型 | 机房 IP | **住宅 IP**（境内那台机器的宽带） |
| 政务/银行类站点 | 部分会拒机房 IP | **不会**（住宅 IP 正常通过） |
| 带宽 | 多人共享，晚高峰降速 | **独享**（只有境外这台在用） |
| 费用 | 月付 | 零（境内那台的电费除外） |
| 数据路径 | 经过服务商服务器 | **只经过你和境内那台机器** |
| 可用性 | 7×24 | **依赖境内那台开机** |
| 出问题 | 有客服 | 只有你自己 |

**最大的差别是「住宅 IP」。** 部分政务、银行、票务站点对机房 IP 有额外风控，
这正是自己搭建的意义。代价是可用性完全取决于对端那台机器。

## 技术选型一句话

```
Tailscale 负责打通两端（NAT 穿透、加密、零配置网络）
hysteria2 负责跑流量（QUIC + 固定速率拥塞控制，高丢包环境下比 TCP 好）
本地代理内核负责分流（只让需要的流量进隧道，其余直连）
```

**为什么不直接用现成的商业加速器** —— 见 [docs/architecture.md](docs/architecture.md)。

## 六个必踩的坑（都在这了）

部署过程中有六个坑，每一个都会让你以为「这套东西不能用」：

1. **MTU：QUIC 首包 1308 字节，虚拟网卡默认 1280 只允许 1252** —— 差 28 字节，
   而且失败是**静默的**（客户端只报超时，服务端零日志，抓包抓不到）
2. **hysteria2 的 `bandwidth.down` 是硬上限**，设多少就发多少，不是「建议值」
3. **`ignoreClientBandwidth: true` 会让固定速率拥塞控制失效**，静默回落到 BBR
4. **Windows 上改 MTU 必须用 `TS_DEBUG_MTU` 环境变量**，`netsh` 会被服务重启覆盖
5. **本地代理内核可能劫持你的隧道进程**，让流量绕远路，速度掉一半
6. **`tls.sni` 填了 IP 地址会握手失败** —— 报 `CRYPTO_ERROR 0x150`，
   看起来像证书或密码问题，实际是 RFC 6066 禁止 SNI 用 IP 字面量

完整说明 + 排查方法：[docs/pitfalls.md](docs/pitfalls.md)

## 快速开始

```powershell
# 0. 把仓库 clone 到两端
git clone <THIS_REPO>

# 1. 在【境内】那台生成服务端配置和证书
#    那台机器的住宅 IP 就是这个方案的出口
.\scripts\setup-server.ps1 -CertHost hysteria.local

# 2. 在【境外】这台生成客户端配置
#    -ServerAddr 填境内那台的 Tailscale IPv4（100.x.x.x），不要填 MagicDNS 名
#    原因：MagicDNS 名可能解析到 IPv6，而 IPv6 的 QUIC 首包需要 1328 字节
.\scripts\setup-client.ps1 -ServerAddr <境内那台的 Tailscale IPv4>

# 3. 两端各装一次看门狗（-Role 不同，不要装反）
.\scripts\install-watchdog.ps1 -Role server    # 在境内那台执行
.\scripts\install-watchdog.ps1 -Role client    # 在境外这台执行

# 4. 在【境外】这台生成分流规则
.\scripts\gen-pac.ps1
```

详细步骤（含新旧方案并存、一条命令回滚）：[docs/deploy.md](docs/deploy.md)
